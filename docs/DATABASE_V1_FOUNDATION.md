# Database V1 Foundation

Database V1 migrations 001 and 002 implement only the operational foundation and ingestion
lineage layers. They do not implement the later canonical, taxonomy, history, quality,
analytics, or serving schemas.

## Schemas and responsibilities

`system` is private operational metadata. It contains pipeline version records, retention
policies, background-job state, and append-only audit events. `ingestion` is the private
evidence and execution layer: approved source configuration, parser versions, crawl runs and
tasks, fetch observations, immutable raw-object references, extraction runs and records, and
sanitized errors.

The lineage is:

```text
Source -> CrawlRun -> CrawlTask -> FetchEvent -> RawObject
                                  -> ExtractionRun -> ExtractedRecord
```

Stable configuration IDs use UUIDs generated by `pgcrypto`'s `gen_random_uuid()`. High-volume
events use `BIGINT GENERATED ALWAYS AS IDENTITY`. All database timestamps are `TIMESTAMPTZ` and
applications must write UTC values.

## Raw evidence and retention

`ingestion.raw_objects` deduplicates evidence by lowercase SHA-256. Small structured JSON
evidence may use the inline JSONB field. Full HTML and other large bodies must use an external
object reference. Rows are append-only from ordinary application code. Expiry and policy
references are metadata only: these migrations do not schedule or perform deletion.

No retention rows are seeded. Unknown retention remains `NULL`; operators must create versioned
policies after review. Fetch failures are observations and never imply that a posting is inactive.

## Security boundary

Both schemas revoke schema privileges from PostgreSQL `PUBLIC`. They are for the owner/migration
role and a future narrowly granted backend service role, not Supabase `anon` or frontend users.
RLS and Supabase role grants are deliberately deferred to a deployment-specific security
migration so local PostgreSQL does not depend on Supabase-only roles. JSON metadata, headers,
audit values, and errors must be sanitized and must never contain credentials, cookies, tokens,
private bodies, or secret-bearing stack traces.

## Migration commands

Set `DATABASE_URL` to PostgreSQL 16, then run:

```powershell
alembic upgrade head
alembic current
alembic downgrade 20260726_0001
alembic upgrade head
```

Migration 001 creates the extension, private schemas, and seven foundation tables. Migration 002
adds seven ingestion execution/lineage tables. Downgrade 002 leaves the foundation intact.

## Legacy baseline decision

This repository is pre-production. The metadata-driven Phase 3 revision
`20260724_0001_phase3_schema` was replaced with a clean explicit production baseline because it
used `Base.metadata.create_all()` and could silently change historical DDL. Prototype ORM classes
remain available to the current API and SQLite unit tests, but Alembic no longer creates those
prototype canonical tables. No migration drops them from an existing database.

Existing local prototype databases should be recreated. Preserve any required pilot artifacts,
upgrade a clean PostgreSQL database, and reimport pilot data only after the later canonical V1
migrations exist; migrations 001 and 002 intentionally have no canonical job destination.
